# Git 提交信息规范（强制执行）

> 本文件是本仓库提交信息的强制规则，所有 `git commit` 必须严格遵守。
> 内容与 [`提交规范.txt`](../../提交规范.txt) 保持一致；如有冲突，以本文件为准。

## 1. 适用范围

- 适用于本仓库所有分支、所有开发者与 AI 会话产生的提交。
- 每次提交前必须检查暂存区：`git status`、`git diff --cached`。
- 只提交与本次任务相关的文件，不得夹带无关改动、密钥或生成物。

## 2. 语言要求

- 简短描述、正文、脚注必须使用简体中文。
- 类型（Type）和范围（Scope）标识符保持英文。
- 技术术语首次出现使用“中文（English）”格式，如“断点续传（Resume Upload）”。
- API、SDK、HTTP、gRPC 等通用缩写可直接使用英文。

## 3. 提交格式

```text
<类型>(<范围>): <简短描述>

- <正文条目 1>
- <正文条目 2>

[可选脚注]
```

## 4. 类型（Type）

| 类型 | 说明 |
|------|------|
| feat | 新功能 |
| fix | 修复 Bug |
| docs | 文档变更 |
| style | 代码格式（不影响功能） |
| refactor | 重构（非新功能、非 Bug 修复） |
| perf | 性能优化 |
| test | 添加或修改测试 |
| chore | 构建过程或辅助工具变更 |
| ci | CI/CD 配置变更 |
| revert | 回滚提交 |

## 5. 范围（Scope）

- 使用小写英文，取自模块、目录或功能名，例如 `spider`、`ecommerce`、`docker`、`docs`、`agents`。
- 范围应能快速定位改动所属模块。
- 跨多个模块且无法归一时可省略范围，但需在正文说明影响面。

## 6. 强制规则

1. 简短描述不超过 50 个字符，不以句号结尾，使用中文。
2. 正文每个条目以 `- ` 开头，每行不超过 72 个字符。
3. 正文说明“做了什么”和“为什么”，不描述“怎么做的”。
4. 不得使用英文描述功能变更，技术内容应翻译为中文表达。
5. 一个提交只做一件事，无关改动拆分提交。
6. 破坏性变更必须在脚注写 `BREAKING CHANGE:`，说明文字使用中文。
7. 禁止空提交，禁止提交密钥、`.env`、数据库、缓存、大文件。
8. 未明确要求不得 `commit` / `push`，不得改写历史、强制推送或跳过 hooks。

## 7. 正例

```text
feat(spider): 新增淘宝商品详情解析适配器

- 支持从详情页提取价格、销量与店铺信息
- 补充离线 fixture 与单元测试，便于回归验证
```

```text
fix(ecommerce): 修复购物车越权访问问题

- 查询购物车前校验订单归属，避免读取他人数据
- 补充越权拦截测试用例

BREAKING CHANGE: 购物车接口现在要求登录并校验 user_id
```

## 8. 反例

```text
update code
```

```text
feat: 增加功能
```

```text
fix(spider): 修复bug。
```

```text
feat: add new parser
```

以上反例分别缺少类型/范围/中文描述、缺少范围、描述以句号结尾、功能变更使用英文描述，均不允许。

## 9. 提交前检查清单

- [ ] 已执行 `git status` 与 `git diff --cached` 确认暂存内容
- [ ] 只包含预期文件，无密钥、`.env`、数据库、缓存、大文件
- [ ] 标题格式为 `<类型>(<范围>): <简短描述>`
- [ ] 简短描述为中文且不超过 50 个字符
- [ ] 正文条目以 `- ` 开头且每行不超过 72 个字符
- [ ] 破坏性变更已写 `BREAKING CHANGE:` 脚注
- [ ] 代码已通过语法检查与测试
